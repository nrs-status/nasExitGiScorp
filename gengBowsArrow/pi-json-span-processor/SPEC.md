# pi-json-span-processor — Output Specification

This document is the authoritative behavioural specification of
`pi-json-span-processor` (see `src/Main.hs` for the implementation).

## 1. Input

The program reads a JSON-lines event stream on stdin: one JSON object per
line, emitted by `pi --mode json`. Each input event must have a string
`"type"` field.

Accepted event types:

| Event type              | Role                                            |
|-------------------------|-------------------------------------------------|
| `session`               | Streamed out unmodified (verbatim line).        |
| `agent_start` / `agent_end`             | Begin / end an `agent` span.    |
| `turn_start` / `turn_end`               | Begin / end a `turn` span.      |
| `message_start` / `message_update` / `message_end` | Begin / accumulate / end a `message` span. |
| `tool_execution_start` / `tool_execution_update` / `tool_execution_end` | Begin / accumulate / end a `tool_execution` span. |
| `agent_settled`         | Discarded silently.                             |

Any other event type is an **error**: a message is written to stderr and the
program exits with status 1. The same happens for invalid JSON lines, lines
without a string `"type"` field, structurally malformed nesting (e.g. an
`agent_end` without a matching `agent_start`), and
`tool_execution_*` events whose `toolCallId` has no matching open span.

## 2. Span hierarchy

```
agent (agent_start .. agent_end)
 └─ turn (turn_start .. turn_end)
     ├─ message (message_start .. message_end)
     └─ tool_execution (tool_execution_start .. tool_execution_end)
```

- A `turn` must be inside an open `agent`; a `message` or
  `tool_execution` must be inside an open `turn`.
- Multiple `tool_execution` spans may be open at once (parallel tool
  calls); they are tracked in a map keyed by their `toolCallId`.

## 3. Unique ids

Every span id is generated by the program as `"span-N"`, where `N` is a
counter starting at 1 and incremented once per span, in the order the
`*_start` events are observed. Parent ids reference these generated ids.

## 4. Timestamps

The `start` field of a span is the wall-clock time (ISO-8601, e.g.
`2026-09-10T04:27:01.449Z`) at which the program observed the `*_start`
event; the `end` field is the wall-clock time at which it observed the
matching `*_end` event. They are **processing timestamps**, not event
timestamps carried by the input.

## 5. Output lines

Output is JSON-lines on stdout; each output value is one line.

### 5.1 `session` passthrough

`session` events are copied to stdout byte-for-byte (same line, same field
order).

### 5.2 `agent` span

Emitted on `agent_end`:

| Field    | Type   | Description                  |
|----------|--------|------------------------------|
| `span`   | string | `"agent"`                    |
| `id`     | string | unique generated span id     |
| `start`  | string | start timestamp              |
| `end`    | string | end timestamp                |

### 5.3 `turn` span

Emitted on `turn_end`:

| Field      | Type             | Description                          |
|------------|------------------|--------------------------------------|
| `span`     | string           | `"turn"`                             |
| `id`       | string           | unique generated span id             |
| `start`    | string           | start timestamp                      |
| `end`      | string           | end timestamp                        |
| `parentId` | string           | id of the enclosing `agent` span     |

### 5.4 `message` span

Emitted on `message_end`:

| Field            | Type             | Description                                  |
|------------------|------------------|----------------------------------------------|
| `span`           | string           | `"message"`                                  |
| `id`             | string           | unique generated span id                     |
| `start`          | string           | start timestamp                              |
| `end`            | string           | end timestamp                                |
| `parentId`       | string           | id of the enclosing `turn` span              |
| `content`        | string           | Concatenation of all intermediate `message_update` delta payloads (see §6.1). |
| `contentBlocks`  | array of objects | **Full structured content** of the message (see §6.2). |
| `usage`          | object           | All details of the API cost during this span (see §7). |

### 5.5 `tool_execution` span

Emitted on `tool_execution_end`:

| Field      | Type             | Description                                  |
|------------|------------------|----------------------------------------------|
| `span`     | string           | `"tool_execution"`                           |
| `id`       | string           | unique generated span id                     |
| `start`    | string           | start timestamp                              |
| `end`      | string           | end timestamp                                |
| `parentId` | string           | id of the enclosing `turn` span              |
| `toolName` | string           | `toolName` of the executed tool              |
| `isError`  | boolean          | `isError` of the `tool_execution_end` event (defaults to `false`) |
| `content`  | string           | Merged text of the tool result (see §6.3).  |
| `usage`    | object           | API cost details (see §7)                    |

## 6. Content accumulation

### 6.1 `content` (string) of a `message` span

All intermediate `message_update` events are accumulated by concatenating
the incremental payloads of their `assistantMessageEvent`: the `delta`
field of `text_delta`, `thinking_delta` and `toolcall_delta` variants
(other variants such as `*_start` / `*_end` markers are ignored).  At
`message_end`, if the event's `message.content` contains non-empty text
blocks, the concatenation of those text fields is used instead; otherwise
the accumulated update stream is used.

### 6.2 `contentBlocks` (structured) of a `message` span

The full parsed content of the message, as an ordered array of block
objects:

| Block type   | Object shape                                                   |
|--------------|----------------------------------------------------------------|
| `text`       | `{"type":"text","text":"…"}`                                   |
| `thinking`   | `{"type":"thinking","thinking":"…"}`                           |
| `toolCall`   | `{"type":"toolCall","id":"…","name":"…","arguments":{…}}`      |

Construction rules, in decreasing priority:

1. **Authoritative passthrough.** If `message_end`'s `message.content`
   is a non-empty array, it is passed through verbatim (the pi-native
   block format above; a string `content` is wrapped as a single `text`
   block).
2. **Stream reconstruction.** Otherwise blocks are accumulated from the
   `assistantMessageEvent` of intermediate `message_update` events, keyed
   by their `contentIndex` (output ordered by that index):
   - `text_start` / `text_delta` / `text_end` build a `text` block; deltas
     are concatenated, and the authoritative `content` payload of
     `text_end` (when present) overrides the concatenated deltas.
   - `thinking_start` / `thinking_delta` / `thinking_end` build a
     `thinking` block under the same rules (the thinking text is stored in
     the `thinking` field).
   - `toolcall_start` / `toolcall_delta` / `toolcall_end` build a
     `toolCall` block: `id` and `toolName` come from `toolcall_start`; the
     partial-JSON argument fragments sent in `toolcall_delta` payloads are
     concatenated and **decoded** into the parsed `arguments` object (if
     the fragments do not form valid JSON, the raw string is reported in
     an `argumentsRaw` field instead); the authoritative `toolCall`
     payload of `toolcall_end` (when present) overrides the whole block.
3. If neither source yields blocks, `contentBlocks` is `[]`.

### 6.3 `content` (string) of a `tool_execution` span

All intermediate `tool_execution_update` events are accumulated by merging
the text blocks (`{type:"text",text:…}`) of their cumulative
`partialResult` snapshots (pi sends full snapshots, so the merged result is
the latest snapshot when it extends what is accumulated, otherwise genuine
deltas are concatenated).  At `tool_execution_end`, the text blocks of the
event's `result` field (when non-empty) are used instead.

## 7. `usage` object (API cost details)

For `message` spans: the `usage` object observed during the span.
`message_update` events carry cumulative `usage` snapshots; the last one
seen is kept.  When `message_end`'s `message.usage` is present, that
authoritative value is used instead.

For `tool_execution` spans: usage snapshots are not reported on
`tool_execution_*` events, so the `usage` object is all zeros
(`message_update` usage snapshots belong to `message` spans).

The output `usage` object contains, leniently (fields may be absent in the
input):

| Field         | Type            | Present          |
|---------------|-----------------|------------------|
| `input`       | number          | always (default `0`) |
| `output`      | number          | always (default `0`) |
| `cacheRead`   | number          | always (default `0`) |
| `cacheWrite`  | number          | always (default `0`) |
| `totalTokens` | number          | always (default `0`) |
| `reasoning`   | number          | only when present in the input |
| `cost`        | object          | verbatim when present in the input (`{input, output, cacheRead, cacheWrite, total}`) |

## 8. Object key order

`object` fields are emitted in alphabetical key order by the JSON encoder
(e.g. `"contentBlocks"`, `"content"`, `"end"`, `"id"`, `"parentId"`,
`"span"`, `"start"`, `"usage"`).

## 9. Exit status

- `0` when the whole stream was processed successfully (EOF).
- `1` on any error listed in §1, after writing
  `pi-json-span-processor: error: <message>` to stderr.

## 10. Example

Input (abridged):

```json
{"type":"message_start","message":{"role":"assistant","content":[]}}
{"type":"message_update","assistantMessageEvent":{"type":"toolcall_start","contentIndex":0,"id":"call_1","toolName":"bash"}}
{"type":"message_update","assistantMessageEvent":{"type":"toolcall_delta","contentIndex":0,"delta":"{\"command\": \"echo hello\"}"}}
{"type":"message_end","message":{"role":"assistant","content":[{"type":"toolCall","id":"call_1","name":"bash","arguments":{"command":"echo hello"}}],"usage":{…}}}
```

Output:

```json
{"content":"{\"command\": \"echo hello\"}","contentBlocks":[{"arguments":{"command":"echo hello"},"id":"call_1","name":"bash","type":"toolCall"}],"end":"2026-09-10T04:27:02.617Z","id":"span-4","parentId":"span-2","span":"message","start":"2026-09-10T04:27:01.815Z","usage":{…}}
```
